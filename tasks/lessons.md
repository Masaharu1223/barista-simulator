# 開発時の教訓

## 抽出中止機能: ユーザーが説明した「物の流れ」はそのまま素直にモデル化する (2026-08-14)

**何が起きたか**: 「抽出中にボタンを再度押すと中止でき、出てきたショットはゴミ箱に捨てる。
間違えた場合も捨ててから再抽出する」という依頼に対し、2回続けて誤った実装をした。

1. 1回目: 「中止＝満タンのショットが即座に出てくる（早送りで完了）」と実装。
   → 待たずに満タンのショットを得られる「ズル」になっていた。
2. 2回目: 「ズルができる」という指摘を受け、逆に振れすぎて「中止＝ショットは一切出ない」と
   実装した。
   → ユーザーが最初に説明していた「捨てる」という操作自体が成立しなくなり、
   「その時点での量を残して、プレイヤー自身で捨てて、再度ボタンを押す」という
   本来のイメージと違う、と再度指摘された。

**本来の仕様**: 中止した時点までの進捗（量）をそのままショットとしてトレイに残す。
ただし満タンではないので、そのショットはカップへは注げない＝捨てることしかできない。
これで「ズルにならない」（待たなければ使えるショットは手に入らない）ことと、
「捨てる→再度ボタン」というユーザーが最初から説明していた操作の両方が同時に成立する。

**教訓**: ユーザーが「残す／捨てる／押し直す」のように具体的な“物の流れ”を言葉で説明している
ときは、その言葉が指す対象（今回なら「中止した時点のショットという物理的な実体」）を
省略・単純化せず、そのままドメインモデルに落とし込む。曖昧さを自分の判断（「ズル防止だから
無くそう」のような）で埋めて振り子のように行ったり来たりするのではなく、指摘された制約
（今回は「満タンにならないこと」）を、ユーザーが最初に描写していた流れ（「残る→捨てる→
やり直す」）の上に**足し算**で反映する。1つの指摘は「今の実装の何が問題か」であって、
「その手前にあった別の要素まで消してよい」という意味ではない。

**次から気をつけること**:
- 修正指示が来たら、今回の指摘だけでなく、それ以前にユーザーが説明していた要件全体を
  もう一度読み返し、両方を同時に満たす一つの仕様を探す
- 「◯◯すると××が起きる」という一見ゲーム的なズルの指摘は、大抵「量」や「状態」を表現する
  データが足りていない（今回なら Shot に "完成しているか" の概念がなかった）サインなので、
  機能自体を消すより先に、モデルに足りないフィールドがないかを疑う
